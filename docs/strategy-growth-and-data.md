# サイト戦略：集客（A）とデータ資産の完成度（C）

対象サイト: 資格カタログ / shikaku-master.jp
作成日: 2026-07-16
スコープ: 本ドキュメントは 2 軸に絞る — **A. 集客（SEO・記事コンテンツ）** と **C. データ資産の完成度**。
（収益化 B・UX/回遊 D は別途。ただし A・C が両者の前提になる。）

---

## 0. 全体診断（なぜ A と C なのか）

現状のサイトは「**配管（データ×SEO構造）はほぼ完成しているが、そこに流すコンテンツと、データ自体の完成度に穴がある**」状態。

| 資産 | 状態 | 評価 |
|---|---|---|
| 静的量産の生成基盤（`build_pages.py`） | 完成・CI自動デプロイ | ◎ 強い土台 |
| 構造化データ（JSON-LD／sitemap／canonical／noindex衛生） | 実装済み | ◎ 参入障壁 |
| 検索意図ハブ（feature 17・vs 51・bunya 20） | 実装済み | ◯ 未活用の資産 |
| 資格詳細 862件の公式データ | 整備済み | ◎ コア資産 |
| **記事コンテンツ** | **1本のみ** | ✕ 最大の空白（＝A） |
| **データの完成度**（要確認297・seed216・合格率202/862） | 未完 | △ 守りの穴（＝C） |
| データ鮮度フロー | 人手・一括日付依存 | △ 陳腐化リスク（＝C） |

**A と C は独立ではなく相互補強する**:
データが完成する（C）ほど、記事で根拠として引用できる事実が増え（A）、記事が増える（A）ほど、詳細ページ・ハブへ内部リンクが集まりデータ資産の SEO 評価が上がる（C の回収）。よって **両輪で回す**のが最も効率が良い。

---

## A. 集客戦略（SEO・記事コンテンツ）

### A-1. 現状の診断

- 記事は `content/articles/dokugaku-kokka-shikaku.md` の **1本のみ**。集客の主戦場（情報収集フェーズの検索）がほぼ空白。
- 一方で **記事量産の仕組みは既にある**:
  - front-matter（`title / h1 / slug / description / date / related`）付き Markdown → `build_articles()` が HTML 化。
  - `[[c-XXXX]]` / `[[c-XXXX|表示名]]` で**資格詳細への内部リンク**を自動生成。
  - `related:` で「この記事で紹介した資格」ブロック、feature ハブへの「関連ガイド」ナビも自動。
  - 記事一覧 `article/index.html`、パンくず・Article JSON-LD も自動。
- つまり **1本 md を書けば SEO 対応済みページが増える**。ボトルネックは仕組みではなく「本数」と「テーマ設計」。

### A-2. キーワード／コンテンツクラスタ設計

既存の**ハブ（feature / vs / bunya）と詳細ページ**を「クラスタの中心（ピラー）」とし、記事をそこへ流し込む **トピッククラスタ戦略**を採る。記事は必ず既存 URL 群へ内部リンクさせ、リンクエクイティをコア資産に集約する。

#### クラスタ1：目的・悩み起点（情報収集フェーズ＝流入の主戦場）
既存 feature ハブを記事で肉付けする。検索ボリュームが大きく、比較検討前の広いユーザーを取れる。

20 分野それぞれに「分野まるごとガイド」を用意し、`bunya/*` の一覧を記事側から要約・解説してハブを強化する（例：IT／建築・設備／医療／会計金融／福祉）。優先は検索需要と保有件数の大きい **IT・建築・機械電気・会計金融・医療**。

例：受験料が安い国家資格／合格率で見る難易度ランキング／CBTで通年受験できる資格一覧の読み方。

> 目標本数の目安：**フェーズ1で 10本、四半期で 20〜30本**。まず 1〜13 の「ハブ肉付け系」から着手すると、既存資産への内部リンクが最短で増える。

### A-3. 内部リンク／テクニカル SEO の強化

既存基盤は強いが、**逆方向・相互リンクの薄さ**が伸びしろ。

1. **ハブ／詳細 → 記事への逆リンクを自動化**
   現状リンクは「記事 → 詳細・ハブ」の一方向。`build_feature_pages()` / `build_detail()` に「関連記事」枠を追加し、`related:` を逆引きして詳細・feature から記事へ送る（回遊・クロール改善）。
2. **記事同士のリンク（クラスタ内リンク）**
   同一クラスタの記事を相互リンクし、ピラー↔クラスタの網を作る。
3. **トップの記事枠拡張**
   現状トップの「記事・コラム」は 1 件表示。本数増に合わせ新着 5〜8 件＋「記事一覧へ」を出す（`build_index()`）。
4. **`lastmod` を sitemap に付与**
   記事・詳細の更新日（`date` / `source_checked_at`）を sitemap の `<lastmod>` に反映し、再クロールを促す。
5. **薄い index ページの継続監視**
   `is_indexable_detail()` の noindex 衛生は良い設計。C でデータが増えたら自動で index 化されるので、**「noindex → index 昇格数」を A の KPI に含める**。
6. **パンくず・FAQ 以外の構造化強化余地**
   詳細に `HowTo`（受験までの流れ）や、ランキング系に `ItemList` JSON-LD を検討（リッチリザルト獲得）。

### A-4. 制作ワークフロー（本数を回す仕組み）

- **テンプレ化**: front-matter ひな型＋「導入→3条件/選び方→データ根拠（`[[c-XXXX]]`引用）→FAQ→関連ガイド」の構成を標準化。
- **データ駆動の下書き**: 記事で挙げる資格・数値は CSV から機械抽出（例：`feature` 判定ロジックを再利用して候補資格リストを生成）。事実は必ず既存の公式一次データを引用し、**推測を書かない**方針を記事にも適用（サイトの信頼性ポリシーと一貫）。
- **品質ゲート**: `[[c-XXXX]]` の指す slug 実在チェックを `validate.py` に追加（リンク切れ防止）。

## C. データ資産の完成度

### C-1. 現状の診断（実測）

| 穴 | 件数 | 中身 |
|---|---|---|
| 区分「要確認」 | **297** | ほぼ全て `未判定(一次情報での確認待ち)`。IT 69／語学 49／ものづくり 41 に集中 |
| 未整備 `status=seed` | **216** | ものづくり 54／IT 29／美容サービス 25。統一実施団体のない民間任意資格が中心 |
| 合格率（`pass_rate`）空 | **660**（published の 77%） | 団体非公表が構造要因。ただし人気資格でも 11件は受験者数がある＝埋める価値大 |
| 鮮度（`source_checked_at`） | 759件が **2026-06-18 の一括日**、216件は空 | 単一バッチ日付＝陳腐化タイミングが一斉に来るリスク |

### C-2. 優先順位づけ（需要加重で埋める）

全件を均等に埋めるのは非効率。**「検索需要 × 現状の穴」でスコアリング**して上位から着手する。

- **需要シグナル**（既にデータにある）: 受験者数（`applicants`）、feature/vs ハブに載っている、`related_slugs` 参照数、大分類の保有件数。
- **穴シグナル**: 要確認である／seed である／`pass_rate` 空／`fee` 空。

→ **需要が高いのに穴がある資格**を最優先バックログにする。

#### 優先バックログ（着手順）

1. **人気×合格率空の 11件**（技術士各部門・全商英語検定・DIYアドバイザー等）を先に埋める。受験者数がある＝検索需要がある。
2. **要確認 297件の区分確定**。特に **IT(69)・語学(49)** は記事クラスタ2・3の対象と重なるため、A と同じ資格を優先すると相乗効果。判定は `classify_rules.py` のルール拡張＋公式一次情報での個別確認。
3. **seed 216件のうち「実施団体が特定できる」ものを published 化**。ものづくり・IT・美容サービスから、公式試験データが存在するものを順次。統一団体がなく整備不能なものは **明示的に「整備対象外」ステータス**を付け、無理に埋めない（サイトの誠実さポリシーを維持）。
4. **合格率・受験者数の面的拡充**。公表がある資格に限り、年度・回を併記して追加（`SOURCES.md` の既存ルール踏襲）。

### C-3. 鮮度維持フロー（陳腐化対策）

現状 `source_checked_at` が実質単一日付で、更新が属人的。以下で「腐りにくい」体制にする。

1. **鮮度の可視化**: `validate.py` に「`source_checked_at` が N か月以上前」の資格を警告出力する検査を追加。CI で棚卸しリストが常に見える状態に。
2. **年度更新項目の分離管理**: 受験料・合格率・受験者数・日程は「年度で変わる」フラグ的に扱い、優先再確認対象に。制度・URL・試験形式は変化が遅いので後回しでよい。
3. **半自動化の検討**: 公式サイトが自動取得をブロックする制約（`SOURCES.md` 記載）があるため全自動は困難。だが「再確認が必要な資格の抽出」までは自動化できる。人手は確認作業に集中させる。
4. **確認日をページとSEOに反映**: 詳細の「最終更新」表示と sitemap `<lastmod>` を `source_checked_at` 連動にし、鮮度をユーザーとクローラー双方に示す（A-3 の 4 と共通施策）。

### C-4. データ品質ガードレール（維持）

既存の厳格ポリシー（公式一次情報のみ・空欄容認・推測禁止・確認日管理）は**そのまま堅持**。これは競合に対する信頼性の差別化要因。C の拡充は「穴を埋める」ことであって「品質基準を緩める」ことではない。`validate.py` の検査を拡張して基準を機械的に担保する。

## ロードマップ（A・C を両輪で回す）

各フェーズで **同じ資格群を A と C で同時に扱う**ことで相乗効果を最大化する。

### フェーズ1（〜1か月）: 基盤づくりと最初の相乗
- C: 人気×合格率空の 11件を埋める／`validate.py` に鮮度警告＋`[[c-XXXX]]`実在チェックを追加。
- A: クラスタ1・2から記事 10本（士業系・IT・お金・目的別）。
- 横断: ハブ／詳細 → 記事の逆リンク自動化、トップ記事枠拡張、sitemap `<lastmod>`。

### フェーズ2（1〜3か月）: 面で広げる
- C: 要確認 297件のうち IT・語学・会計金融を優先確定（記事対象と一致させる）。seed の published 化を分野単位で。
- A: 記事を四半期累計 20〜30本へ。bunya ピラー強化記事（IT・建築・機械電気・会計金融・医療）。
- 横断: noindex→index 昇格の計測、クラスタ内相互リンクの網を完成。

### フェーズ3（3か月〜）: 仕組みで回す
- C: 鮮度棚卸しを定例化（CIの警告リスト起点）。年度更新項目の再確認サイクル確立。
- A: データ駆動の記事候補生成を半自動化し、月次で安定生産。上位記事のリライト・拡充。

## KPI（測定指標）

| 軸 | 指標 | 初期の見方 |
|---|---|---|
| A 集客 | 記事本数、記事経由の内部リンク数、index 対象ページ数、検索表示回数/CTR（Search Console） | まず「本数」と「index 数」で先行指標を追う |
| A 品質 | 記事あたりの詳細ページ被リンク数、リッチリザルト獲得（FAQ/ItemList） | 構造の充実度 |
| C 完成度 | 要確認の残数（297→）、seed 残数（216→）、`pass_rate`/`applicants` 充足件数、published 件数 | 穴の縮小を絶対数で |
| C 鮮度 | `source_checked_at` が N か月超の件数、`<lastmod>` 反映率 | 陳腐化の抑制 |
| 相乗 | noindex→index 昇格件数、記事↔詳細↔ハブの相互リンク網羅率 | A と C が噛み合っている証拠 |

> 計測の前提: **Google Search Console／Analytics の導入状況を確認**。未導入なら最初にこれを入れないと A の効果測定ができない。
